## いま何ができているか

配信アーカイブのURLから見せ場候補をランキングするWebアプリ。
`start_highlight.bat` を実行するとローカルサーバが立ち、ブラウザが開く。
Discordボットとは無関係で、`bot.py` は1行も変更していない。

- チャットの盛り上がり検出（時間帯ごとの平常値と比べたスコア）
- 「草」「驚き」などカテゴリ別ランキング、任意ワード検索
- 音声のラウドネス解析（任意・チャットと照合してSEの誤検知を落とす）
- コメント密度グラフ、タイムスタンプ/チャプター/CSV書き出し
- 取得したチャットと音量列はキャッシュし、設定変更時は再取得なし
- **編集ソフトへの書き出しに「自動カット」「テロップ」（2026-10-26 追加・任意）**
  文字起こしの単語の時刻から沈黙を詰め、カット後の時刻で SRT を作る。下の「自動カットとテロップ」を参照

詳しい仕組みと設定は `README.md` を参照。テストは205件（`python -m unittest discover -s stream_highlight/tests -t .`）。

## 自動カットとテロップ（2026-10-26）

書き出す区間だけを文字起こしし、沈黙を詰めたクリップ列と SRT を作る。
詳しくは README の「自動カットとテロップ」。

| ファイル | 役割 |
| --- | --- |
| `transcribe.py` | エンジン（Qwen3-ASR / faster-whisper）、5分分割、ループ除去、キャッシュ、依存チェック |
| `autocut.py` | 単語の時刻から「残す部分」を決める（余白・ピーク保護・短い断片の吸収） |
| `retake.py` | 言い直しの判定（Claude API・任意）。`python -m stream_highlight.retake` で疎通確認 |
| `subtitles.py` | SRT（1行16文字・2行・0.7〜5秒・カット点で分割） |
| `editexport.py` | `Timeline`（フレームの丸めを1か所に集約）、カット版の XML / EDL |
| `autoedit.py` | 区間ごとの 文字起こし→カット→書き出し の流れ |
| `compare_engines.py` | 2エンジンの比較（1つずつ読み込み・解放） |
| `samples/` | Premiere 確認用の XML / SRT と、その生成スクリプト |

判断したこと:

- 両方 OFF のときは、出力も処理の流れ（その場で返す同期処理）も従来のまま。
  ON のときだけ `jobs.submit_task` でバックグラウンドにする
- 変更前の出力を `tests/data/legacy_*` に保存し、1文字も変わらないことをテストで確かめている
- 依存は `requirements-transcribe.txt` に分けた。本体の自動導入には入れない
- exe 版には含めない（spec で torch などを明示的に除外）
- ffmpeg は PATH 優先、無ければ imageio-ffmpeg
- 言い直し削除のモデルは `.env` の `STREAM_HIGHLIGHT_RETAKE_MODEL`（既定 `claude-opus-5-5`）

開発機（RTX 4060 Ti 8GB）での導入状況: qwen-asr 0.0.6 と faster-whisper 1.2.1 を導入済み。
導入前の一覧は リポジトリ直下の `before.txt`（pip freeze）。torch は 2.5.1+cu124 のまま
（CUDA 有効を確認）。transformers は 5.5.3 → 4.57.6、accelerate 1.13.0 → 1.12.0、
huggingface_hub 1.10.1 → 0.36.2 に下がった。

実機で確認できたこと（合成音声の検証用動画で。数値は README の「開発機での実測」）:

- 両エンジンとも GPU で動き、アプリと同じ API 経路（ジョブ・進捗表示・キャッシュ）で XML と SRT が出る
- エンジンを画面で切り替えても落ちない（whisper→Qwen、Qwen→whisper の両方）
- 180秒を超える区間の分割と時刻のつなぎ直し（264秒で確認）
- 発話を削るカットは無し

- **Premiere での読み込み**（2026-10-27、利用者が確認）: `samples/` のカット版 XML と SRT で、
  カット点・テロップ・マーカーがすべて正しく読めた。サンプルの架空の発話は整数秒に揃えてある
  （秒の途中から始まっていたため、テロップの数字がカウンタより最大1秒遅れて見えていた）

## 実配信テスト（2026-10-27）

実際の配信で、見せ場の上位の区間だけを両エンジンで書き出して比べる。詳しくは README の
「実際の配信での通し試験」。

```
python -m stream_highlight.realtest "<配信URL>" --top 5
```

| ファイル | 役割 |
| --- | --- |
| `realtest.py` | 解析→上位の区間だけダウンロード→先頭の実測→Qwen / whisper で書き出し→点検→`report.md` |
| `notify.py` | Discord の Webhook への投稿（`.env` の `STREAM_HIGHLIGHT_DISCORD_WEBHOOK`、任意） |
| `editexport.py` / `autoedit.py` | 区間ごとに別の動画ファイルを参照できるように（`segment["media"]`）。1本の動画での出力は従来のまま |
| `server.py` / `static/` | `/api/realtest/progress` と、画面上部の進捗バー |

判断したこと:

- **区間は HLS（H.264 + 音声）で落とす。** YouTube の DASH（https）に ffmpeg で途中から飛び込むと
  先頭から順に読むことになり、2時間4分の位置の区間が30分たっても始まらなかった（CPU 4秒、出力なし）。
  音声だけの DASH でも同じく2分半で失敗。HLS なら区間（2分）が約35秒
- **先頭のずれは二重に対策**: `--force-keyframes-at-cuts` で指定の時刻で切り、さらに実際の先頭を測って
  その値で換算する。基準は DASH 音声の目次（sidx）から範囲指定で取った音声（プレーヤーと同じ時刻、
  区間とは別の経路）。HLS の音声断片は時刻を持たず、`EXTINF` も0.1秒に丸めてある（実長と最大約0.1秒違う）
  ため、HLS どうしで照らすと同じ向きのずれを見落とすおそれがあった。DASH が無いとき（Twitch など）は
  HLS の音声で照らす
- 進み具合は段階の重さ（区間1つあたり ダウンロード 1.0、Qwen 0.5、whisper 0.1、読み込みは別）で%にし、
  `progress.json` に書く。画面は5秒ごとに読む。15分更新が無ければ「止まっているかも」と出す
- スマホでの確認は Discord 通知にした（アプリを LAN に公開する案は、同じネットワークの他人にも
  見えるため見送り）。Webhook は Discord の URL だけを受け付け、送れなくてもテストは止めない
- 出力先 `stream_highlight/realtest/` は git の管理外

実測（結川ユイナさんの推理配信 `XMK_FuEHbDY`、約5時間31分、見せ場の上位5件 × 前後1分 = 10分）:

| | Qwen | whisper |
| --- | --- | --- |
| 文字起こし | 78.5秒 | 14.7秒 |
| 全体（読み込み込み） | 104.3秒 | 17.8秒 |
| 元の長さ → カット後 | 10:00 → 7:04 | 10:00 → 6:20 |
| カットの数 | 56 | 50 |
| テロップの数 | 206 | 128 |
| おかしなテロップの候補 | 5件 | 2件 |
| 誤検出の候補 | 17件（ほぼ「Qwen だけが拾った」） | 4件 |

- 区間の先頭のずれ: 5区間とも ±0.000秒（一致度 0.98〜1.00、基準 DASH）
- 再エンコードにかかる時間: 区間1つのダウンロードが 8.4秒 → 33.4秒（区間5つで約2分増）。
  この配信の HLS では再エンコードなしでもずれは +0.000秒だった
- 事前の確認: HLS で取った音声は DASH との差が +0.007秒 / 0.000秒。映像の HLS 断片の PTS は
  `EXTINF` の合計と1フレーム以内で一致（映像と音声の時刻は揃っている）
- おかしなテロップの候補は、両エンジンとも「ワンワンワン」のような実際の発話（鳴きまね・口癖）を
  繰り返しとして拾ったものが中心。意味不明な文字列は無し
- テロップの数の差（206 / 128）は、Qwen だけが拾った発話による。本人の発話を whisper が
  取りこぼしたのか、Qwen がゲーム内の声などを拾ったのかは未判定

**結論（2026-10-27、利用者が Premiere で判断）: Qwen のほうが良かった。** 既定のエンジンは
Qwen のまま（`transcribe.DEFAULT_ENGINE`）。処理時間は whisper の約5倍（10分ぶんで約1分半）かかる。
どの点が良かったか（カット・テロップ・拾った発話）の内訳は未聴取。

未検証:

- 実配信での Qwen の気になる点（ゲーム内の声を拾っていないか、詰めすぎ・詰め残し）。
  利用者が時刻付きで挙げたら調整する
- Twitch での区間ダウンロードと、HLS の音声を基準にした照合
- 画面の進捗バーは表示の確認のみ（実行中の実データでの表示は、キャッシュを使った10秒の再実行でだけ確認）

## チャンネルごとの設定（2026-10-27）

目的: 担当チャンネルの投稿動画（結川ユイナさんは配信を編集した13〜61分の動画が7本）に、
カット感・テロップ量・動画の長さを合わせる。投稿動画の編集データ（`.prproj` / XML）は前任者に
依頼中で、届くまでの間に「チャンネルごとに設定を持ち、配信から自動で切り替える」入れ物を先に作った。
詳しくは README の「チャンネルごとの設定」。

| ファイル | 役割 |
| --- | --- |
| `profiles.py` | 保存・読み込み（`channel_profiles.json`）、項目と範囲の制限、ID → 表示名の順で探す |
| `subtitles.py` | `CaptionStyle`（1行の文字数・行数・最短/最長表示）。既定値は従来の定数のまま |
| `sources.py` | `StreamInfo.channel_id` を追加（YouTube は `channel_id`、Twitch は `uploader_id`） |
| `server.py` / `static/` | `/api/profile`（取得・保存・リセット）、テロップの体裁と「書き出す見せ場の数」の入力、チャンネルの表示 |
| `realtest.py` | 同じ設定を使う（`--top` / `--margin` の指定が優先） |

判断したこと:

- 保存するのは書き出し側（区間・カット・テロップ・エンジン）だけ。解析の設定（感度など）は、
  チャンネルが分かる前に解析が走るので、今回は対象外
- 設定に無い項目は各道具の既定値（画面とスクリプトで既定が違う項目があるため、値を埋めずに上書きだけ持つ）
- 同じ配信を解析し直したときは、手で変えた値を上書きしない（チャンネルが変わったときだけ切り替える）
- 何も保存していなければ従来と同じ出力（既存のテストと、既定の `CaptionStyle` で同じテロップになることを確認）

確認したこと: テスト13件を追加（合計205件）。画面で「保存 → 別チャンネル扱いで既定値に戻る →
開き直すと保存した値に戻る」を確認。`realtest.py` が保存した設定を読むことも確認（確認用に保存した設定は消した）。

## 直したバグ（実機で判明したもの）

- `requirements.txt` の日本語コメント → 日本語WindowsのpipがUnicodeDecodeError
  （pipはロケール既定のcp932で読むため、このファイルに非ASCIIを置いてはいけない）
- 起動バッチが、原因を問わず「Pythonが入っているか確認してください」と誤案内
- Twitchのnull応答で `AttributeError` → 解析全体が失敗
- チャットログの入れ子nullで落ちる箇所を全面的に防御（1行の崩れで全体を落とさない）
- **書き出したXMLの解像度が違う**
  `samplecharacteristics`（解像度）を書いていなかったため、Premiere が
  シーケンスを自前の既定値で作っていた。シーケンス側（`video/format`）と
  素材側（`file/media/video`）の両方に書く。`format` は `track` より前。
  配信から取れた解像度を初期値にし、手元のファイルと違う場合に備えて
  画面から直せるようにした（配信1440pでも1080pで落とすことがある）。
- **更新と無関係なファイルを触っただけで、自動更新が永久に止まる**
  起動側で `git diff --quiet` を見て止めていたため、`bot.py` を編集しただけで
  更新が入らなくなっていた。`git pull --ff-only` は上書きするファイルが
  あるときだけ失敗し、名前も教えてくれる。先回りをやめて git に任せた。
- **非表示起動が無言で失敗する**（起動の層を減らして解決）
  - VBScript が無効化されると `.vbs` は何も起こさずに終わる
  - bat → vbs / PowerShell → cmd と重ねるほど、引用符や無効化で黙って死ぬ
  - → `pythonw.exe run_app.py --update` の一本道にした。pythonw は
    コンソールを持たないため、黒い画面を隠す仕掛け自体が不要になる
  - `git` が認証を聞くと、非表示のまま永久に待つ → `GIT_TERMINAL_PROMPT=0`
  - 失敗しても画面に何も出ない → 例外を必ずログに書き、メモ帳で開く
- **版表示が嘘をついて、更新したのに古い画面を見続ける**（二度やった）
  1. `_build_id.txt`（exeビルドの置き土産）を `.git` より優先していた
  2. `/api/capabilities` がその場で `.git` を読んでいた → 起動後に `git pull` すると
     「ディスク上の版」を「動作中の版」として答えてしまう。
     そのため起動側が「同じ版が動いている」と誤認し、更新した版を起動せず
     古いサーバのブラウザを開くだけになっていた（新機能が出ない原因）
  → 起動時に `RUNNING_VERSION` を確定させ、`on_disk` と `restart_needed` を別に返す。
  起動側は `on_disk` を返さない相手を「版を答えられない古い版」と見なして
  入れ替える。ポートが空いたかどうかはHTTPの無応答ではなく実際の `bind` で判定する
  （応答しないまま居座るプロセスを「居ない」と誤判定すると、次の起動が
  ポート使用中で落ちる）

## 手元での動かし方

`start_hidden.cmd` をダブルクリック。中身は `pythonw.exe run_app.py --update`
の一行で、更新・ライブラリ導入・起動を `run_app.py` が受け持つ。
記録は `stream_highlight\app.log`。失敗したらメモ帳で勝手に開く。

原因が分からないときは `start_highlight.bat` を直接ダブルクリックする。
黒い画面は出るが、どこで失敗したかがそのまま読める。

`start_highlight_silent.vbs` も残してあるが、**Windows 11 では VBScript が
段階的に無効化されているため、ダブルクリックしても何も起きないことがある**
（Microsoftは既定で無効化する段階を2026〜2027年としている）。
そのため VBScript に依存しない `start_hidden.cmd`（PowerShell 経由）を正とする。

古い版が動いたままなら、開き直すだけで入れ替わる（古い方に終了を頼み、
同じポートを引き継ぐ）。終了を頼めなかったときだけ別のポートで立ち上げる。

exe 版は作った時点で固まるので、更新には `build_exe.bat` での作り直しが要る。

Python 3.10 / pip は導入済みであることを確認済み。
