# 配信ハイライト抽出ツール

配信アーカイブのURLを貼るだけで、チャットが普段より盛り上がった瞬間を
ランキングにして返す。切り抜き素材を探すために数時間の配信を頭から見る、
という作業をなくすためのもの。

YouTube と Twitch のアーカイブに対応。

## 使い方

`start_highlight.bat` をダブルクリックすると、必要なライブラリを入れて
サーバを立ち上げ、ブラウザが開く。

手動で起動する場合:

```
pip install -r stream_highlight/requirements.txt
python -m stream_highlight.server
```

ブラウザで URL を貼って「解析」を押すと、

- コメント密度のグラフ（コメグラフ相当）
- 盛り上がった順の見せ場ランキング
- 「草」「驚き」などカテゴリ別のランキング
- 任意のワード（`www`、`かわいい` など）で絞った出現タイミング

が出る。時刻をクリックすると、配信のその場面が新しいタブで開く。

「音声も解析」にチェックを入れると、配信者の声が大きくなった瞬間も併せて見る
（音声のダウンロードが要るので、チャットだけより時間がかかる）。

## 見せ場の決め方

単純なコメント数では、視聴者が多い時間帯ばかりが上位に来てしまう。
そこでこのツールは「その時間帯の平常運転と比べてどれだけ跳ねたか」で順位を付ける。

1. コメントを5秒刻みで数える
2. 前後30秒の合計を取り、その瞬間の勢いとする
3. 前後10分の**中央値**を平常値とする（盛り上がり自体に引きずられないよう平均は使わない）
4. `スコア = (勢い - 平常値) / √(平常値 + 1)` を計算する
   コメント数はポアソン的にばらつくので平常値の平方根で割ると、
   静かな時間帯と賑やかな時間帯を同じ物差しで比較できる
5. スコアの高い順に、近すぎるピークをまとめて並べる

チャットは配信者の映像より数秒遅れて反応するので、切り出し範囲は
ピークの少し前（既定30秒前）から始まる。この前後の余白は設定で変えられる。

過疎チャットで「3コメント」が1位になるのを防ぐため、
窓あたり5コメント未満の箇所は候補から外している。

## Twitch特有の扱い

### システム通知を除外する

TwitchのVODチャットには、サブスク告知・ギフト・視聴連続記録・レイドといった
システム通知が本人の発言と同じ形で混ざる。これらは切り抜き素材にならないうえ、
短時間に集中するため偽の見せ場を作ってしまう。そこで通知部分を切り離し、
盛り上がりの判定からも代表コメントからも外している。

通知に本人のひとことが添えられている場合（例:
`○○ subscribed with Prime. They've subscribed for 43 months! ajak0nHi`）、
後半の「ajak0nHi」は本物のコメントなので残す。

除外した件数は画面上部に「通知 N件を除外」と出る。

### チャンネル絵文字

Twitchのチャンネル絵文字は `○○Www` `○○Lul` `○○Kek` のような名前が多い。
語頭の `www` だけを見ると拾えないので、語中の `www` も草として扱う
（URLの `www` は直後が `.` なので対象外）。

## 音声解析

### 何を見ているか

ffmpeg の `ebur128` フィルタが出すモーメンタリラウドネス（LUFS、400ms窓・100ms刻み）を使う。
波形の振幅ではなく人間の聞こえ方に合わせた値なので、「声が大きくなった」を素直に拾える。

ラウドネスは既にデシベル（対数）なので、チャットのようなポアソン正規化ではなく、
「平常音量から何dB上がったか」を全体のばらつき（MAD）で割ってスコアにしている。

平常音量には中央値ではなく **0.8分位** を使う。基準を
「普段しゃべっているときの音量」に置くため。中央値だと、間や無音の多い配信で
そちらに引き下げられ、普通にしゃべっているだけで「音量が上がった」ことになってしまう。
合成データでの比較では、叫び以外の場所の跳ねが 2.5dB から 0.8dB に下がった
（叫びの検出数は変わらず）。

### なぜチャットと照合するのか

**音量だけでは、配信者の声とゲームのSEを区別できない。**
アーカイブの音声はマイクとゲーム音が混ざった1本のトラックなので、
爆発音・銃声・BGMの盛り上がりが、叫び声とまったく同じように音量ピークを作る。
FPSやアクションゲームでは、音量ピークの大半がSEになる。

そこで、音量が跳ねた箇所のうち **「直後にチャットが実際に増えた」ものだけ** を採用する。
SEにはチャットが反応しないので、これが誤検知フィルタとして働く。

判定は「音声ピークの前後20秒で、実コメント数がどれだけ増えたか」をポアソンzで測る。
単に「後ろのチャットが多いか」を見ると、たまたま賑やかな箇所を拾ってしまうため、
前後を比べて「後ろだけ増えた」ことを要求している（ランダムなゆらぎは前後どちらにも同じだけ出る）。

### どのくらい効くか

合成データ（チャット無反応の音量ピーク48箇所）で測った、しきい値ごとの誤通過率:

| チャット照合の厳しさ | SEが誤って通る割合 |
| --- | --- |
| 1.0 | 12% |
| 1.5 | 2% |
| **2.0（既定）** | **0%** |

同じ設定で、本物の反応がどこから拾えるか:

| 追加コメント数 | チャット単独のスコア（3.0で見せ場） | チャット増加量（2.0で採用） |
| --- | --- | --- |
| 10件 | 1.38 ✗ | 1.89 ✗ |
| 12件 | 1.76 ✗ | 2.17 ✓ |
| 14件 | 2.14 ✗ | 2.43 ✓ |
| 18件 | 2.89 ✗ | 2.93 ✓ |
| 25件 | 4.22 ✓ | 3.71 ✓ |

つまり音声解析が効くのは、**チャットが12〜19件程度しか動かず、
チャット単独ではしきい値に届かないが、配信者ははっきり声を上げていた**箇所。
チャットが大きく盛り上がった箇所は元から拾えているので、
音声はそこに「声も +17dB 上がっていた」という裏付けを添える役割になる。

画面には「音量が跳ねた箇所 N件 → チャットも反応していたのは M件（K件を除外）」と出るので、
その配信でフィルタがどれだけ働いたかは毎回確認できる。

### コメントが少ない配信では照合できない

照合は「音量が上がった直後にコメントが増えたか」で判定するため、
**そもそもコメントがほとんど流れない配信では成立しない**。
毎分2件未満の場合は、判定を試みずにその旨を画面に表示する。

この場合でも、各候補に付く「声 +◯dB」のバッジと、
グラフに重なる音量の線はそのまま使える。

### 限界

- **これは合成データでの測定であり、実配信での精度ではない。** 実際の誤検知率は
  ジャンルに強く依存する。雑談配信では素直に効き、SEの多いアクションゲームでは
  除外される箇所が増える。音ゲーのようにBGMが常時大音量だと、
  平常値が高くなって何も検出されないこともある。
- マイクとゲーム音の分離はしていない。分離すれば精度は上がるが、
  3時間の音声に対して処理が重くなりすぎる。
- 音声のダウンロードが必要なので、チャットだけの解析より時間がかかる
  （3時間配信で回線次第、おおむね数分）。一度取れば `cache/` に保存され、
  設定を変えた再解析では再ダウンロードしない。

## 設定

画面下の「解析の設定」で以下を変えられる。チャットは保存済みなので、
変更しても再ダウンロードは起きず、すぐ結果が出る。

| 項目 | 意味 |
| --- | --- |
| 感度 | 低くすると候補が増える（既定3.0） |
| まとめる間隔 | これ以内のピークは1件にまとめる |
| ピークの前/後 | 切り出し範囲の余白 |
| 反応をまとめる窓 | 勢いを測る幅。短くすると一瞬の爆発に、長くすると継続した盛り上がりに反応する |
| 音量のしきい値 | 音声のピークと見なす基準（音声解析時のみ） |
| チャット照合の厳しさ | 上げるとSEの誤検知が減るが、控えめな反応も落ちる |

## グラフの操作

- ドラッグ: その範囲に拡大
- ダブルクリック / 全体表示: 元に戻す
- ホイール: 拡大縮小
- 候補マーカーをクリック: 一覧の該当項目を選択
- 何もない場所をクリック: その時刻の配信を開く

## うまく取得できないとき

診断コマンドで、どこで詰まっているかを調べられる。

```
python -m stream_highlight.diagnose <配信のURL>
```

Twitchなら、使えるClient-IDを順に試して、それぞれが何を返したかを表示する。
保存済みの音量データがあれば、その分布も出す。

```
python -m stream_highlight.diagnose <配信のURL> --audio
```

`--audio` を付けると取得の確認を飛ばして、音量データの分布だけを見る。
平常値の取り方を調整するときに使う。

失敗した場合は生の応答を `twitch_debug.json` に保存するので、
その内容が原因究明の手がかりになる。

### Twitch の Client-ID について

TwitchのGQLは Client-ID によって整合性チェックの扱いが変わり、
古いIDは `failed integrity check` で弾かれることがある。
そのため本ツールは複数のIDを順に試し、実際に通ったものを使う。

- `ue6666qo983t…` — yt-dlp が現在使っている値（既定）
- `kimne78kx3nc…` — 旧Web版の値（予備）

取得の前に必ず単発のリクエストで疎通を確かめてから、
区間を分けた並列取得に入る。いきなり並列で叩くと、
弾かれたのか混んでいるのか区別がつかなくなるため。

## 制限

- **チャットリプレイがある配信のみ**。チャットを無効化している配信や、
  通常の投稿動画からは何も取れない。
- **メンバー限定・限定公開には非対応**（ログインが必要なため）。
- Twitch の VOD チャットは公式APIが廃止されているため、Web版が使っている
  GQL エンドポイントを叩いている。Twitch 側の仕様変更で動かなくなる可能性がある。
  その場合は `diagnose` コマンドの出力で状況が分かる。
- 音声解析は**音声だけのトラックがある配信のみ**。無い場合は、数GBの映像を
  黙って落とさずエラーにする。
- 音声解析には ffmpeg が必要。`pip install imageio-ffmpeg` で同梱版が入る
  （`requirements.txt` に含まれている）。チャットだけの解析に ffmpeg は要らない。

## キャッシュ

取得したチャットと音量列は `stream_highlight/cache/` に圧縮して保存される。
同じ配信を再解析するときはダウンロードを省略する。
不要になったら画面上部の履歴から削除するか、フォルダごと消してよい。

## テスト

```
python -m unittest discover -s stream_highlight/tests -t .
```

合成チャットに仕込んだ盛り上がりを検出できるか、
チャットのパーサが実際のレスポンス構造を扱えるか、
音量ピークのうちSEを弾いて本物の反応を残せるか、
API 一式が動くかを確認している（ネットワークには出ない）。
ffmpeg がある環境では、生成した音声ファイルを実際に通す試験も走る。
