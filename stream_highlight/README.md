# 配信ハイライト抽出ツール

配信アーカイブのURLを貼るだけで、チャットが普段より盛り上がった瞬間を
ランキングにして返す。切り抜き素材を探すために数時間の配信を頭から見る、
という作業をなくすためのもの。

YouTube と Twitch のアーカイブに対応。

## 使い方

起動のしかたは用途で選ぶ。

| 起動方法 | 更新 | 黒い画面 | Python |
| --- | --- | --- | --- |
| **`start_hidden.cmd`**（おすすめ） | 起動のたびに自動 | 出ない | 要 |
| `start_highlight.bat` | 起動のたびに自動 | 出る（原因を読むとき用） | 要 |
| `start_highlight_silent.vbs` | 起動のたびに自動 | 出ない | 要 |
| `StreamHighlight.exe`（exe化したもの） | **されない** | 出ない | 不要 |

**開発中は `start_hidden.cmd` が楽。** 起動のたびに `git pull` で
最新になるので、更新のたびに作り直す必要がない。
デスクトップにショートカットを作っておくとよい。

`start_hidden.cmd` の中身は `pythonw.exe run_app.py --update` の一行。
pythonw はコンソールを持たない Python なので、黒い画面が一瞬も出ない。
更新・ライブラリの導入・起動は全て `run_app.py` の中で行う。

`start_highlight_silent.vbs` は同じことを VBScript でやっていた古い形。
**Windows 11 では VBScript が段階的に無効化されており、ダブルクリックしても
何も起きないことがある。** 残してはあるが、使うのは `start_hidden.cmd`。

exe は「Pythonの無いPCでも動く」「フォルダごと持ち運べる」ための形。
作った時点のコードで固まるので、更新するには `build_exe.bat` で作り直す。

手元に編集中のファイルがあっても、更新は取り込む。`git pull --ff-only` は
上書きしてしまうファイルがあるときだけ失敗し、その名前も教えてくれるので、
判断は git に任せている。自分で先回りして止めると、更新と無関係なファイル
（`bot.py` など）を触っただけで更新が永久に入らなくなる。

手動で起動する場合:

```
pip install -r stream_highlight/requirements.txt
python -m stream_highlight.server
```

画面を出さない起動（`start_hidden.cmd` / `.vbs`）では、失敗しても何も見えない。
そのため `stream_highlight\app.log` に必ず書き出し、失敗したときは
そのログをメモ帳で開くようにしてある。

それでも分からないときは `start_highlight.bat` を直接ダブルクリックする。
黒い画面は出るが、どこで止まったかがそのまま読める。

ブラウザで URL を貼って「解析」を押すと、

- コメント密度のグラフ（コメグラフ相当）
- 盛り上がった順の見せ場ランキング
- 「草」「驚き」などカテゴリ別のランキング
- 任意のワード（`www`、`かわいい` など）で絞った出現タイミング

が出る。時刻をクリックすると、配信のその場面が新しいタブで開く。

## 編集ソフトへの書き出し

`編集ソフトへ書き出す` を押すと、候補の前後だけを切り出したシーケンスを
作れる。3時間の配信が20分程度になるので、編集はその中だけで済む。

- 書き出すのは**いま画面に表示されている候補だけ**。カテゴリやワードで
  絞ってから押せば、その分だけのシーケンスになる
- 重なる区間はまとめる（同じ場面が二重に並ばないように）
- クリップ名は**元配信のタイムコード**（`01 00:25:00:00`）
- 各ピークにシーケンスマーカーが立つ（Premiere なら Shift+M で次へ）

**フレームレートと解像度は、手元の動画ファイルと同じ値にする。**
これがそのままシーケンス設定になる。配信から取れた値を初期値に入れてあるが、
配信が1440pでも手元には1080pで落としていることがあるので、必ず確かめる。
`動画ファイルの場所` を入れておくと、Premiere が素材を自動でつなぐ。

形式は2つ。XML（FCP7 xmeml v4）は素材の場所と解像度まで書けるので自動で
つながる。読み込めなかったときは EDL を使う。EDL はどの編集ソフトでも通るが、
素材は手でつなぐ必要がある。

**Premiere が実際に読めるかは未検証**（XMLの構造とフレーム計算は検算済み）。

## 自動カットとテロップ（任意）

書き出しパネルの「自動カット」「テロップ」にチェックを入れると、書き出す区間の
**中身**も整える。**`動画ファイルの場所` を入れたときだけ**使える。
どちらも外せば、これまでと1文字も変わらない XML / EDL がその場で返る。

- **自動カット**: 喋っていない間を詰める。1区間が複数のクリップになり、
  クリップ名は `01-03 00:25:12:10`（区間01の3つ目、元配信のタイムコード）。
  ピークのマーカーはカット後の位置に付け直す
- **テロップ**: 配信者の発言を文字起こしして、XML と同じ名前の `.srt` を一緒に保存する。
  時刻はカット後のシーケンス上の時刻
- **言い直しも削除**（任意・既定OFF）: Claude API に言い直しの「前の側」を判定させて消す

ズームやSEは付けない。

### 仕組み

**3時間の配信全体は処理しない。** 書き出す区間だけを ffmpeg で音声
（16kHz・モノラル）として切り出し、文字起こしする。区間ごとに数十秒〜数分かかるので、
バックグラウンドで処理し、何区間目か・モデルの初回ダウンロード中かを画面に出す。

**沈黙は音量では判定しない。** 配信の音声はマイクとゲーム音が1本に混ざっているので
（上の「音声解析を見送った経緯」）、ffmpeg の silencedetect では喋っていない所を
見分けられない。文字起こしが返す**単語ごとの時刻**を発話区間とし、その間を見る。

| 設定（「解析の設定」） | 既定 | 意味 |
| --- | --- | --- |
| この秒数を超える沈黙を詰める | 1.5秒 | 発話と発話の間がこれより長ければ詰める |
| カット点の前後に残す余白 | 0.15秒 | 語尾や息継ぎを切らないため |
| ピークの前後この秒数はカットしない | 5秒 | 喋っていなくても、ゲーム画面で何か起きて視聴者が反応している場面がある。切り抜きではそこが一番大事 |

- カットした結果 0.5秒未満の断片が残るときは、消さずに隣の断片とまとめる
- 単語が1つも取れなかった区間は詰めない（文字起こしの失敗と区別できないため）
- 区間の頭と終わりの長い沈黙も詰める

テロップは1行16文字・最大2行で、句読点や語の切れ目で折る。
表示は最短0.7秒・最長5秒。発話がカット点をまたぐときは、そこでテロップを分ける。
カットで消えた所の語は出さない。

**Premiere は FCP7 XML に埋め込んだテキストを正しく読めないことが多い**ので、
テロップは XML に入れない。SRT を `ファイル > 読み込み` で読み込み、
キャプショントラックとしてシーケンスに置く。

フレームへの丸めは `editexport.Timeline` の1か所で行い、XML・EDL・SRT の全てが
同じ値を使う。別々に丸めると1フレームずつずれて、隙間や重なりができ、
テロップも映像とずれていくため。

### 文字起こしエンジン

「解析の設定」で切り替えられる。どちらも「テキスト＋語ごとの開始・終了秒」を返す
共通の形にしてあるので、エンジンを足すのも `transcribe.py` の中だけで済む。

| エンジン | 位置づけ | 理由 |
| --- | --- | --- |
| **Qwen3-ASR-1.7B ＋ Qwen3-ForcedAligner-0.6B**（既定） | 本命 | 雑談・エンタメ系の日本語実音声のベンチマークで最も精度が高い（CER 14.0%）。複数話者やノイズにも比較的強い。どちらも Apache 2.0 |
| faster-whisper large-v3-turbo | 予備 | 導入が簡単で速いが、存在しない語を付け足す・同じ語を繰り返す失敗が報告されている |

- **ForcedAligner は1回の処理が最大5分。** ただし qwen-asr の公式実装は、時刻を付けるとき
  180秒ごとに区切っている。そこで長い区間は**180秒以内**に分けて処理し、時刻をつなぎ直す
  （ライブラリの中で勝手に分け直されないように、こちらで先に分ける）。
  さらに VRAM の空きが少なければ短く区切る（下の実測を参照）。
  分割点は上限の手前の中で一番静かな所（喋りの切れ目であることが多い）
- Qwen の日本語の時刻は単語ごと・句読点なしで返る。全文から句読点を戻し、
  「漢字・カタカナの並び＋続くひらがな」を1つにまとめて文節に近い単位にする
  （今日は / ホラーゲームを / やっていきます）。0.3秒以上の間がある所では必ず分ける
- GPU（CUDA）があれば float16、なければ CPU で動く。**VRAM が足りないときは落とさず CPU に切り替える**
- 読み込むエンジンは**同時に1つだけ**。切り替えるときは前のものを解放してから読む（VRAM 8GB を想定）
- 同じ語句が3回以上続く**ループ**は、1回分だけ残して取り除く。ゲーム音やBGMが混ざると
  どちらのエンジンでも起こる。1文字の繰り返し（「ははは」「www」）は笑いなので残す
- 結果は区間ごと・エンジンごとに `cache/transcripts/` へ保存する。カットやテロップの設定を
  変えても文字起こしはやり直さない。保存するのは後処理前の出力なので、後処理を直しても再利用できる。
  動画ファイルの大きさか更新時刻が変われば、別物として処理し直す

### 導入

**本体の `requirements.txt` には入れていない**（数GBになるうえ、使わない人には不要なため）。
起動時の自動導入（`run_app.py`）も触らない。使うときだけ別に入れる。

```
pip install -r stream_highlight/requirements-transcribe.txt --dry-run
pip install -r stream_highlight/requirements-transcribe.txt
```

**先に CUDA 版の torch を入れておく**こと。torch が無い状態で入れると、
PyPI から CPU 版の torch が入ってしまう。`--dry-run` で torch が入れ替わらないことを
確かめてから入れる。

注意: `qwen-asr` は transformers を **4.57.6 に固定**している（accelerate と
huggingface_hub も古い版に下がる）。同じ Python で transformers の新しい版を
使う別のものがあれば、そちらに影響する。

足りないものがあると、チェックボックスが押せなくなり、何が足りないかが画面に出る。
アプリ全体は落ちない。

**ffmpeg** は PATH にあればそれを使い、無ければ `imageio-ffmpeg` に同梱されたものを使う。
imageio-ffmpeg を選んだのは、pip だけで入り（管理者権限もPATHの設定も要らない）、
Windows / Mac / Linux で同じ手順になるため。winget などで入れた ffmpeg があれば、そちらを優先する。

モデルは初回に Hugging Face から自動でダウンロードされる
（Qwen は2つ合わせて約6.5GB、whisper は約1.6GB。`%USERPROFILE%\.cache\huggingface` に入る）。

### 言い直しの削除

リポジトリ直下の `.env` に `ANTHROPIC_API_KEY` があるときだけ使える
（`.env.for-partner` などの派生ファイルは読まない）。区間ごとに、時刻付きの文字起こしを
Claude API に渡し、言い直しの「前の側」の語の範囲を返してもらう。

- 使うモデルは `.env` の `STREAM_HIGHLIGHT_RETAKE_MODEL` で変えられる（既定 `claude-opus-5-5`）
- 失敗したら言い直しの削除だけを諦め、書き出しは続ける（理由は画面に出る）
- 3割以上の語を消せと返ってきたら、判定がおかしいと見なして使わない
- ピーク前後の保護範囲は、言い直しでも消さない

APIに通るかは、次のコマンドで確かめられる:

```
python -m stream_highlight.retake
```

### エンジンの比較

同じ区間を両方のエンジンで処理し、テキストと処理時間を並べる。
実際の配信素材でどちらを使うか決めるためのもの。

```
python -m stream_highlight.compare_engines "D:\配信\2026-10-20.mp4" --start 1500 --end 1800
```

| 引数 | 意味 |
| --- | --- |
| `--start` / `--end` | 比べる区間（秒）。既定は先頭から5分 |
| `--engines` | 比べるエンジン（既定 `qwen,whisper`） |
| `--out` | 結果をテキストファイルにも保存する |

出力は、エンジンごとの装置（GPU/CPU）・読み込み秒・処理秒・実時間比・語数・
取り除いたループの数と、それぞれの全文。ループを取り除いた場合は、除去前の全文も出す。
エンジンは1つずつ読み込み、終わったら解放してから次を読む。キャッシュは使わない。

選ぶときの目安: ゲーム音が大きい場面・複数人で話している場面・早口の場面を含む
区間で比べる。静かな雑談だけだと差が出にくい。

### 実際の配信での通し試験

配信URLを渡すと、ツールと同じ解析で見せ場を出し、上位の区間だけを両方のエンジンで
書き出す。**配信全体はダウンロードせず、区間付近だけを yt-dlp で取ってくる。**

```
python -m stream_highlight.realtest "https://www.youtube.com/watch?v=XXXX" --top 5
```

| 引数 | 意味 |
| --- | --- |
| `--top` | 書き出す見せ場の数（既定5） |
| `--margin` | 見せ場の前後の秒数（既定60。区間は約2分になる） |
| `--media` | 手元に配信全体の動画があれば、その場所。ダウンロードしない |
| `--engines` | 使うエンジン（既定 `qwen,whisper`） |
| `--out` | 出力先（既定はデータフォルダの `realtest\<サイト>_<動画ID>`） |

出力先にできるもの:

- `<タイトル>_qwen.xml` / `.srt`、`<タイトル>_whisper.xml` / `.srt`
- `parts\`: ダウンロードした区間（`part01_開始秒-終了秒.mp4`）。2回目からは使い回す
- `report.md` / `report.json`: エンジンごとの処理時間・長さ・カット数と、点検結果

区間ごとに別の動画ファイルになるので、XML は区間ごとにそのファイルを参照する
（`segment["media"]`）。クリップ名は元の配信のタイムコードのまま。ダウンロードは
`--force-keyframes-at-cuts` で切れ目を再エンコードし、ファイルの0秒を区間の開始秒に
ぴったり合わせている。1080p までに抑える。

`report.md` の点検は目安で、良し悪しは Premiere で見て判断する。

- おかしなテロップの候補: 同じ語の繰り返し・同じ文字の長い連続・「ご視聴ありがとうございました」
  のような定型文・英字や記号が多いもの
- 誤検出の候補: 片方のエンジンだけが拾った発話、音が大きい所（区間の上位20%）で前後に
  他の語が無い短い語

処理時間はモデルの読み込みを含む。文字起こしはキャッシュが効くので、2回目に流すと
「最初に起こしたときの秒数」を（キャッシュ）付きで表示する。

### 開発機での実測（2026-10-26）

RTX 4060 Ti 8GB。Windows の音声合成（Haruka）で作った、間を挟んだ日本語の独り言
132秒で測った。**ゲーム音もBGMも無いきれいな音声**なので、精度は実配信より高く出る。
実配信でどちらが良いかは、上の比較スクリプトで確かめる必要がある。

| | whisper（large-v3-turbo） | Qwen3-ASR ＋ ForcedAligner |
| --- | --- | --- |
| 読み込み | 3〜5秒 | 約24秒 |
| 文字起こし（132秒） | 2.4秒（実時間の約55倍速） | 15.8秒（約8倍速） |
| VRAM | 小さい | モデルだけで約5.9GB、音声1秒あたり約16MB 追加 |
| 文字誤り率（台本と比較） | 1.4% | 3.5% |
| 主な誤り | 「みなさん→皆さん」程度 | 「探さない→探すない」「今なんか→今難波」 |
| 発話を削ったカット | なし | なし |
| カット点と発話の端の距離 | 最小0.09秒・中央0.27秒 | 最小0.13秒・中央0.18秒 |
| 132秒を詰めた結果 | 83.5秒 | 76.0秒 |

- 合成音声では whisper のほうが正確で速かった。ベンチマーク（雑談・エンタメ系の実音声）とは
  逆の結果だが、合成音声は発音がはっきりしていて whisper の得意な条件に近い。結論は実配信で出す
- Qwen の時刻のほうが発話の端に正確で、詰め方もきれい（沈黙を残さない）
- whisper は語の終わりを実際より0.1〜0.2秒早く返す。そのままでは余白を足しても
  語尾を削ることがあったので、whisper の語の終わりだけ0.15秒延ばしている
  （そのぶん、沈黙が0.2秒ほど長めに残る）

実機で見つけて直したこと:

- **whisper が GPU で動かない**（`cublas64_12.dll` が見つからない）。ctranslate2 は CUDA の
  ライブラリを同梱していない。CUDA 版の torch が同じ版を持っているので、そこを読ませる。
  それでも読めないときは CPU に切り替えて続ける
- **同じプロセスで whisper → Qwen と切り替えると、プロセスごと落ちる**
  （`Could not load symbol cudnnGetLibConfig`）。ctranslate2 が自前の古い cuDNN を
  先に読むため。whisper を読む前に torch の cuDNN を読ませて解決（両方の順で確認済み）
- **Qwen で180秒を一度に処理すると VRAM（8GB）を超え、2倍近く遅くなる**。
  読み込み後の空きから区切る長さを決める（開発機では約50秒）。264秒の処理が167秒→31秒になった
- **分割点が語の途中に来ることがあった**（「これかな」が「これかだ」に）。50msの一瞬の
  途切れを無音と取り違えていたので、0.4秒の幅でならして選ぶようにした

### Premiere での確認用サンプル

`stream_highlight/samples/` に、合成データから作った XML と SRT を置いてある。

- `sample_autocut.xml` / `.srt`: 動画の場所を書いていない版（読み込み後に素材をつなぐ）
- `python -m stream_highlight.samples.make_samples --video` を実行すると、
  経過秒数のカウンタが映る10分の確認用動画（`sample_source.mp4`）と、
  それにつながった `sample_linked.xml` / `.srt` ができる

確認のしかた: `sample_linked.xml` を読み込み、`sample_linked.srt` をキャプションとして置く。
テロップは「143秒です。」のように元の配信の秒を読み上げる体裁で、
その秒ちょうど（143.0〜143.9秒）に出る。
**画面のカウンタとテロップの数字が合っていれば、カットも SRT の時刻も正しい。**
シーケンスは 1280x720 / 29.97fps、区間2つ（ピーク200秒・420秒の前後1分）が
22クリップになり、4分→約2分48秒になる。

### exe 版には含めない

torch とモデルで数GBになり、exe の「フォルダごと持ち運べる」という利点を損なうため、
exe 版には文字起こしの依存を**含めない**（`StreamHighlight.spec` で明示的に除外している。
PyInstaller は関数の中の import も拾って同梱してしまうため）。
exe 版ではチェックボックスが押せず、「Python から起動してください」と表示される。

## 見せ場の決め方

単純なコメント数では、視聴者が多い時間帯ばかりが上位に来てしまう。
そこでこのツールは「その時間帯の平常運転と比べてどれだけ跳ねたか」で順位を付ける。

1. コメントを5秒刻みで数える
2. 前後30秒の合計を取り、その瞬間の勢いとする
3. 前後10分の**中央値**を平常値とする（盛り上がり自体に引きずられないよう平均は使わない）
4. `スコア = (勢い - 平常値) / √(平常値 + 1)` を計算する
   コメント数はポアソン的にばらつくので平常値の平方根で割ると、
   静かな時間帯と賑やかな時間帯を同じ物差しで比較できる
5. スコアの高い順に、近すぎるピークをまとめて並べる

チャットは配信者の映像より数秒遅れて反応するので、切り出し範囲は
ピークの少し前（既定30秒前）から始まる。この前後の余白は設定で変えられる。

過疎チャットで「3コメント」が1位になるのを防ぐため、
窓あたり5コメント未満の箇所は候補から外している。

## Twitch特有の扱い

### システム通知を除外する

TwitchのVODチャットには、サブスク告知・ギフト・視聴連続記録・レイドといった
システム通知が本人の発言と同じ形で混ざる。これらは切り抜き素材にならないうえ、
短時間に集中するため偽の見せ場を作ってしまう。そこで通知部分を切り離し、
盛り上がりの判定からも代表コメントからも外している。

通知に本人のひとことが添えられている場合（例:
`○○ subscribed with Prime. They've subscribed for 43 months! ajak0nHi`）、
後半の「ajak0nHi」は本物のコメントなので残す。

除外した件数は画面上部に「通知 N件を除外」と出る。

### チャンネル絵文字

Twitchのチャンネル絵文字は `○○Www` `○○Lul` `○○Kek` のような名前が多い。
語頭の `www` だけを見ると拾えないので、語中の `www` も草として扱う
（URLの `www` は直後が `.` なので対象外）。

## 音声解析を見送った経緯

当初は「配信者の声が大きくなった瞬間」も見る予定で、実装して実配信で検証した。
結論として **入れないほうが良い** と判断し、取り外した（コミット履歴には残っている）。

### やったこと

ffmpeg の ebur128 でモーメンタリラウドネス（LUFS）を100ms刻みで取得し、
平常音量（0.9分位）からの跳ねをスコア化。ただし音声だけでは配信者の声と
ゲームのSEを区別できないため、「音量が上がった直後にチャットが増えたか」で
照合して誤検知を落とす設計にした。

### 分かったこと

| 配信 | 長さ | コメント | 結果 |
| --- | --- | --- | --- |
| Valheim | 11時間49分 | 171件（0.2/分） | コメントが少なく照合が成立しない |
| 格ゲー | 2時間30分 | 2,936件（19.6/分） | 照合は機能。音量ピーク69件中52件（75%）をSEとして除外 |

**誤検知フィルタ自体は設計どおり機能した。** それでも外したのは次の理由:

- 音声だけで見つけた候補（6件）は、切り抜き素材として使えなかった
- 「音声も跳ねた候補だけ」で絞り込んでも、候補の質は変わらなかった
- 一方でコストは大きい。2.5時間の配信で音声のダウンロードに数分、
  ffmpeg の導入も必要になる

つまり **配信者が声を上げてもチャットが動かない場面は、結局のところ見せ場ではない**。
チャットのほうが信号として強く、音声が独自に見つけられるものは残っていなかった。

同じことをやろうとする人のために書いておくと、音声を活かすなら
マイクとゲーム音の分離が要る。混ざった1本のトラックのままでは、
この結論を超えられないと思われる。

## 設定

画面下の「解析の設定」で以下を変えられる。チャットは保存済みなので、
変更しても再ダウンロードは起きず、すぐ結果が出る。

| 項目 | 意味 |
| --- | --- |
| 感度 | 低くすると候補が増える（既定3.0） |
| まとめる間隔 | これ以内のピークは1件にまとめる |
| ピークの前/後 | 切り出し範囲の余白 |
| 反応をまとめる窓 | 勢いを測る幅。短くすると一瞬の爆発に、長くすると継続した盛り上がりに反応する |
| 最初の◯分を無視 | 配信開始直後の挨拶ラッシュを候補から外す（既定は0＝何も隠さない） |

## exe にまとめる

Python も git も要らない形にできる。`build_exe.bat` をダブルクリックすると、
`dist\StreamHighlight\` に一式ができあがる。初回は10分ほどかかる。

```
dist\StreamHighlight\
  StreamHighlight.exe    ← これを実行する
  data\                  ← チャットの保存先。app.log もここ
  _internal\             ← 中身。触らなくてよい
```

**黒いコンソール画面は出ない。** 終了するときは、画面右上の「終了」ボタンを押す。
ブラウザのタブを閉じただけではアプリは動いたままなので注意。

もう一度 exe を起動したときに既に動いていれば、二重に立ち上げず
ブラウザを開くだけにしている。

**フォルダごとどこへ移してもそのまま動く。** 別のPCにコピーしても、
そちらに Python が入っていなくても動く。
ショートカットをデスクトップに作っておくと楽。

### exe化で気をつけた点

- exe化すると `sys.executable` は自分自身を指すため、`python -m yt_dlp` の形で
  yt-dlp を呼べなくなる。そこで `StreamHighlight.exe --ytdlp …` と呼ぶと
  yt-dlp として振る舞う入口を用意している（`run_app.py`）。
- 保存先は exe の隣の `data`。書き込めない場所（Program Files など）に
  置かれた場合だけ `%LOCALAPPDATA%\StreamHighlight` に逃がす。
- yt-dlp は配信サイトごとの抽出器を実行時に読み込むため、
  `collect_submodules("yt_dlp")` でまとめて同梱している。
  これを省くと「対応していないURL」と言われる。
- 配布物でもバージョンが分かるよう、ビルド時にコミットIDを埋め込む。
- コンソールを出さない設定では標準出力の行き先が無くなる。そのまま print すると
  失敗するうえエラーも残らないので、`data\app.log` に向けている。
  起動しない・落ちるときはこのファイルを見る。
- コンソールが無いと終了できなくなるため、画面に「終了」ボタンを置いた。
- 子プロセス（yt-dlp）にも `CREATE_NO_WINDOW` を指定している。
  指定しないと、取得のたびに黒い画面が開いてしまう。
- それでも環境によってコンソールが付くことがあるため、起動時に
  `GetConsoleWindow` で自分のコンソールを探して隠している。
  ただしコマンドプロンプトから起動した場合など、他と共有している
  コンソールは利用者の画面なので触らない（`GetConsoleProcessList` で判定）。

### 黒い画面が出るとき

`data\app.log` の先頭に、起動時の状態が必ず記録される。

```
--- 起動 2026-09-18T08:57:22 ---
コード      : a79e3ab
実行ファイル: ...\StreamHighlight.exe
コンソール  : なし
```

- **コード** が古ければ、ビルドし直していないか、別の場所にコピーした
  古いexeを起動している
- **コンソール** が「隠した」なら、一瞬出てから消えるのが正しい挙動
- 「あり（他と共有している…）」なら、コマンドプロンプトなどから
  起動している。その画面は利用者のものなので閉じていない

exe を作り直さなくても、開発中は `start_highlight.bat` で従来どおり動く。

## 更新したあとは必ず再起動する

`git pull` でコードを更新したら、**サーバを起動し直す**こと。

画面側（HTML/CSS/JS）はブラウザを再読み込みすれば新しくなるが、
解析の処理は Python が起動時に読み込むため、再起動しないと古いまま動く。
「画面の表示は新しいのに結果が変わらない」ときはこれが原因。

いま動いているコードは、画面下の「解析の設定」を開くと
`動作中のコード: xxxxxxx` として出る。起動時のコンソールにも出る。
この値が `git log --oneline -1` と一致していれば、正しく再起動できている。

## うまく取得できないとき

診断コマンドで、どこで詰まっているかを調べられる。

```
python -m stream_highlight.diagnose <配信のURL>
```

Twitchなら、使えるClient-IDを順に試して、それぞれが何を返したかを表示する。

失敗した場合は生の応答を `twitch_debug.json` に保存するので、
その内容が原因究明の手がかりになる。

### Twitch の Client-ID について

TwitchのGQLは Client-ID によって整合性チェックの扱いが変わり、
古いIDは `failed integrity check` で弾かれることがある。
そのため本ツールは複数のIDを順に試し、実際に通ったものを使う。

- `ue6666qo983t…` — yt-dlp が現在使っている値（既定）
- `kimne78kx3nc…` — 旧Web版の値（予備）

取得の前に必ず単発のリクエストで疎通を確かめてから、
区間を分けた並列取得に入る。いきなり並列で叩くと、
弾かれたのか混んでいるのか区別がつかなくなるため。

## 制限

- **チャットリプレイがある配信のみ**。チャットを無効化している配信や、
  通常の投稿動画からは何も取れない。
- **メンバー限定・限定公開には非対応**（ログインが必要なため）。
- Twitch の VOD チャットは公式APIが廃止されているため、Web版が使っている
  GQL エンドポイントを叩いている。Twitch 側の仕様変更で動かなくなる可能性がある。
  その場合は `diagnose` コマンドの出力で状況が分かる。
- **チャットのみ**を見ている。音声解析は検証のうえ見送った（上記）。

## キャッシュ

取得したチャットは `stream_highlight/cache/` に圧縮して保存される。
同じ配信を再解析するときはダウンロードを省略する。
不要になったら画面上部の履歴から削除するか、フォルダごと消してよい。

## テスト

```
python -m unittest discover -s stream_highlight/tests -t .
```

合成チャットに仕込んだ盛り上がりを検出できるか、
チャットのパーサが実際のレスポンス構造を扱えるか、
API 一式が動くかを確認している（ネットワークには出ない）。

自動カット・テロップのテスト（`test_autoedit.py`）は、文字起こしの結果を合成データで
代用するので、モデルもネットワークも使わない。機能を OFF にしたときの出力が
変更前と1文字も変わらないことは、変更前のコードで書き出した `tests/data/legacy_*` と
突き合わせて確かめている。
